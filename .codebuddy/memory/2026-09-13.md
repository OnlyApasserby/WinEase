### 最终目录结构（约 55 个文件）

- `src/sdk/`：插件 SDK 静态库 `WinEaseSdk`

- `src/app/`：主程序 `WinEase`（exe）

### 关键设计决策
1. **插件只继承 `WinEase::IFeaturePlugin`，不再重复继承 `QObject`**。
   `IFeaturePlugin` 本身继承 QObject，若按 Qt 官方示例写 `public QObject, public IFeaturePlugin`
   会产生二义基类 → `connect()` 调用不明确（C2385）、moc 生成的 `qt_metacast` 转换歧义（C2594）。
2. **`Q_DECLARE_INTERFACE(WinEase::IFeaturePlugin, WinEase_IFeaturePlugin_iid)` 必须写在 IFeaturePlugin.h 末尾**。
   缺它会导致 moc 报 `Undefined interface`，且 `qobject_cast<IFeaturePlugin*>` 无法跨 DLL 生效。
3. 插件契约集中在静态库 `WinEaseSdk`（无任何单例/全局状态），主程序用 `PluginServices` 抽象接口
   向插件注入配置/日志/通知/快捷键能力，避免插件 DLL 与主程序各持一份单例。
4. `PluginManager` 动态插件用 `std::vector<std::unique_ptr<QPluginLoader>>` 持有
   （QList 要求元素可拷贝，装不下 move-only 的 unique_ptr）。
5. 配置目录固定 `%APPDATA%/WinEase`（用 `%APPDATA%` 环境变量解析，而非 QStandardPaths::AppDataLocation，
   后者会变成 `%APPDATA%/WinEase/WinEase`）。
6. 快捷键 id 约定：`<pluginId>::<action>`，主程序自身为 `app::<action>`；持久化到 `[Hotkeys]` 段。
7. 插件配置段为 `[Plugins/<pluginId>]`，启用状态键名 `enabled`。

### 踩坑记录（对后续写代码有复用价值）
- `qt_add_plugin()` **不接受 `SOURCES` 关键字**，源码列表必须直接展开，否则报 “Cannot find source file: .../SOURCES”。
- `QSettings::setIniCodec()` 在 Qt 6 已移除（Qt6 固定 UTF-8）。
- 自定义消息处理器内部再打日志会与自身互斥锁死锁，必须解锁后再 `qCInfo`。
- QToolBar/QMenu 的 `addAction(text, receiver, functor)` 存在重载歧义，用显式 `new QAction` + `connect` 封装更稳。
- moc 的 `Q_INTERFACES` 能正确解析命名空间内的接口（已用最小样例验证）。

## 第四轮：MinGW 迁移可行性评估（用户提问，结论：不迁移）

用户问是否可改用 MinGW 编译（`D:/Qt6-mingw/` 有 MinGW 版 Qt6，未加入 PATH）。

### 实测到的 MinGW Qt 状况
- 版本 **6.8.4**（与 MSVC 那套完全同版本）；编译器 **GCC 16.2**（`mkspecs/qconfig.pri`）
- 目录内**不含 `g++.exe`** → 工具链需单独装 GCC 16.x
- `bin/` 下未见 `libstdc++-6.dll` / `libgcc_s_seh-1.dll` / `libwinpthread-1.dll`
- 模块**比 MSVC 那套更全**（自带 Qt6Multimedia 等），但**仍然没有 Qt6Pdf**
- 全工程检索：**没有** `__try` / `#pragma comment` / `__declspec` → 业务代码基本零改动，
  要改的只有构建系统（这正是"接口+实现分离"的价值）

### 核心结论：致命项是 C++/WinRT 不可用
C++/WinRT 官方只支持 MSVC 与 clang-cl → **D1 决策会作废**，影响 PDF 预览、OCR、媒体控制、
录屏、视频预览；替代方案（DXGI Desktop Duplication / PDFium C API / 砍 OCR）都要额外成本。
另有 7 项迁移成本（GCC 16.x 工具链、UCRT/MSVCRT 口味匹配、调试换 gdb、
dxva2/pdh/wbemuuid 导入库需 gendef+dlltool、`__try` 改 VEH、MinGW 运行库部署、build 目录不能共用）。
收益只有"单文件部署"与"不用自己编译 Qt"，而 MSVC Community 本就免费。

### 用户最终决定（第五轮开头确认）
**保留 MSVC + MSVC 编译的 Qt**，由用户自行补装 QtMultimedia → 记为决策 **D8**。

### 本轮发现并修复的真实缺陷（全部来自自检）
1. **`ApiInformation::IsTypePresent` 在未打包桌面程序中直接崩溃**
   （`winrt/base.h:2948 assert(value)`），因为该 API 面向有"包标识"的应用。
   → 改用 `RoGetActivationFactory` 探测，且请求 `IID_IUnknown` 而非 `IActivationFactory`
   （静态类如 `PdfDocument` 的工厂实现的是自己的静态接口，请求后者会对可用类型误报 `E_NOINTERFACE`）。
   实测 `Windows.Data.Pdf.PdfDocument` 探测为**可用** → P2-02 PDF 预览方案成立。
2. **`std::wstring_view` 作为跨模块字符串接口是脆弱的**（空 hstring 的 `data()` 可能为 nullptr，
   触发 Debug STL 断言）→ 已移除该辅助函数，改由消费方用 `c_str()` + 长度显式处理。
3. **★ 最重要：Debug 构建与 release-only 的 Qt 不兼容**

### 关键设计决策（连同理由已写入 ROADMAP）
1. **钩子装在专用线程**：低层钩子回调运行在安装线程上；装在主线程会让 UI 卡顿连带拖慢全局输入
2. **抽出 SDK 接口层**：插件必须能订阅但**绝不能**自己装钩子（重复回调 + 互相拖慢）——
   这正是 ROADMAP 里"P0 必须先做 HookService"的根本原因
3. **默认投递模式是排队而非同步**：先保证"输入不被拖慢"，需要拦截的功能显式声明 Direct

### 本轮发现的新陷阱（已写入踩坑记录 #15~#17）
1. **★ 不能用 `QEvent::registerEventType()` 跨模块传自定义事件**
   静态库被主程序与每个插件各链接一份，各有一份静态变量 → 各模块拿到的 type id 不同，
   主程序创建的事件插件永远认不出来。用 `QEvent::User + N` 固定偏移也会与其它模块冲突。
   → 改用**lambda 形式的 `QueuedConnection`**：无需统一 type id、无需 `qRegisterMetaType`，
   且接收者析构时 Qt 自动撤销未执行调用。**这是本轮避免掉的最大的坑**（按常规写法实现会极难排查）
2. **线程消息队列必须先创建**：`PostThreadMessage` 对尚无消息队列的线程返回
   `ERROR_INVALID_THREAD_ID`；低层钩子回调也依赖安装线程的消息循环。
   → `PeekMessage(..., PM_NOREMOVE)` 强制创建 + `QSemaphore` 同步"安装完成"，不用 msleep 猜
3. **托盘应用不响应 `CloseMainWindow()`**（关窗即最小化到托盘）——
   导致无法用脚本验证"经关闭窗口的优雅退出路径"，`shutdown()` 里的钩子统计日志需手工验证

   `class QStyleSheetStyle : public QWindowsStyle`（`QtWidgets/private/qstylesheetstyle_p.h`），

### 本次踩到的坑（ROADMAP 踩坑记录 #24~#27）
1. ★ **MIC（强制完整性控制）**：提权进程创建的命名管道默认 High IL 标签，
   普通权限（Medium）进程**禁止写入** → QLocalSocket 连接直接"拒绝访问"。
   QLocalServer（Qt 6.8）无法设置 DACL/标签（Qt 6.9 才有 SocketOptions）。

   客户端 QLocalSocket 不用改。
2. **路径分隔符比较**：QueryFullProcessImageNameW 给 `\`，QFileInfo 给 `/`，
   直接 compare 永远不等 → 比较前 fromNativeSeparators + cleanPath + toLower 归一化。
3. **JSON 会剥 BOM**：hosts 带 UTF-8 BOM，经 QString/JSON 传输丢 3 字节
   → writeHosts replace 增加 `contentBase64` 字节级通道。
4. **安全软件锁 hosts**：连续两次写 hosts，第二次报错误码 5 → 写入失败重试 8×250ms。
5. **TerminateProcess 的 exitCode=1 时 Qt 报 NormalExit 而非 CrashExit**
   → 断言"被终止"不能用 exitStatus，用"60s sleep 1s 内退出 + exitCode==1"。
6. **重编译 helper 前必须退出它**（提权进程锁 exe，普通权限 Stop-Process 失败）
   → 走它自己的 quit 白名单操作最省事（这也顺带验证了 quit）。
7. C++20 `u8"..."` 是 char8_t，不能赋给 const char*（/utf-8 下窄字面量本就是 UTF-8）。

### 为什么先做一整套"端到端自检"而不是只写插件
P0 阶段的自检都是"验原语/验契约"，没有一个能回答"用户装上的插件到底把活干对没有"。
P1 的四个窗口插件都要动**用户真实窗口**，一旦有错就是改坏用户桌面，所以先把测试骨架做出来。

**`tests/feature_smoke` 与 `plugin_smoke` 的关键区别**：前者**不编入任何插件源码**，
运行时用 `QPluginLoader` 加载 `build/bin/plugins` 下**真实的插件 DLL**，
用 `PluginManager::dispatchHotkey("<id>::<action>")` 驱动，再回 Win32 侧读**真实窗口状态**断言。

### 新增基础设施
1. `src/win32/WindowTarget.h/.cpp`：目标窗口解析原语
   - `WindowTargetMode{FollowCursor, LockedWindow}`；`cursorPosition()`；
     `isAcceptableTarget()`；`resolveWindowTarget(mode, locked)`
   - 跟随模式：光标下顶层窗口 → 不可用（压在 WinEase 界面/桌面/任务栏上）则回退前台窗口；

### 本轮发现并修复的真实缺陷（产品代码）
**分屏「居中」每按一次窗口就小一圈**（实测 150% DPI 下每次缩约 18×9 px）：
`centerWindowOnMonitor()` 用 `visualWindowRect()` 量出视觉宽高，却把它当**窗口矩形**交给

### 本轮踩到的测试侧大坑（已写入 ROADMAP 踩坑 #32/#33）
1. **假通过**：置底插件用 `WINEVENT_SKIPOWNPROCESS` 装钩子 → 装钩子进程**自己**产生的 z 序/前台变化
   被过滤，在测试进程里做实验永远走不到"维持"逻辑。**必须让另一个进程触发**：
   探针子进程里再开辅助窗口，先 `SetWindowPos(HWND_TOP)` 抬起目标窗口、再激活辅助窗口；
   子进程抢前台要 `AttachThreadInput` 到当前前台线程，否则前台锁定会拒绝。
2. **假失败**：「跟随鼠标」策略下窗口一移动/一沉底，光标就不在目标窗口上了 → 后续动作静默作用到
   **别的窗口**（可能改到用户真实窗口！）。**每个动作前都必须重新瞄准 + 断言前置条件**，
   并打印"光标在哪/命中了谁/期望是谁"。
3. **时序**：`WINEVENT_OUTOFCONTEXT` 回调是**排队投递**的，抬高窗口后立刻做命中测试可能被迟到的
   回调又压回去 → 命中测试做成最多 3 次重试（每轮先 `processEvents()` 排空积压消息再抬高）。
4. 启用瞬间发出的 `statusMessage` 必须在 `setPluginEnabled()` **之前**订阅，否则收不到
   （第一版因此漏掉了"步长 25%"这条断言）。
