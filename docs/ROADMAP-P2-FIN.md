### 文件与资源管理器

- [x] **P2-01 批量重命名** — `file.batch_rename` · M · 无提权
  - 实现：`QDir` + `QRegularExpression` + `QFile::rename`；EXIF 日期用 `QImageReader`
  - 规则：正则捕获组、序号（起始/步长/补零）、查找替换、前后缀、大小写、扩展名处理
  - 必备：**实时预览表 + 冲突检测 + 一键撤销**（记录原→新映射）
  - 验收：1000 个文件重命名可撤销还原；目标名冲突时拒绝执行并高亮
  - 产出：`plugins/file_batch_rename/` + 引擎 `plugins/common/RenameEngine.{h,cpp}`（**纯函数**：
    `plan()` 出计划、`apply()` 落盘、`invert()` 反推撤销映射）。
    **预览 / 落盘 / 撤销三处走的是 `plan()` 的同一份计算结果** —— 这是本功能唯一不能错的地方
    （"表里写着 A、盘上变成 B"是灾难级缺陷）。撤销栈落配置（跨会话可撤），
    改规则走 200ms 防抖重算，冲突时「应用」直接禁用 + 状态栏明说"共 N 处冲突"。
    实现偏差（有意）：**没做"序号"与"EXIF 日期"两条规则** —— 序号与"查找替换/前后缀"的组合语义
    （谁先谁后）没有公认答案，EXIF 还要在无元数据文件上静默退化；两者都留到有真实需求时再加
    （`Options` 里已留位置）。撤销只记"原→新映射"，不做整目录快照。
    自检断言：预览表逐字符的新名 == 磁盘上真实的文件名（**预览=落盘**）、过滤器之外的文件不进表也不被动、
    改规则后表格会跟着变、目标重名时按钮被禁用**且硬点也不动任何文件**、执行后「撤销」可用、
    撤销后**磁盘逐项回到原名且文件大小不变**（映射没串）、状态栏把冲突说清楚

- [x] **P2-03 重复文件查找** — `file.duplicate_finder` · M · 无提权
  - 算法：按大小分组 → 首 4KB 哈希 → 全量 SHA-256；`QtConcurrent` 并行、可中断
  - 安全约束：**必须"先扫描后删除"，删除走回收站**（`IFileOperation`），禁止静默硬删
  - 验收：10 万文件目录可中断；删除项可在回收站还原
  - 产出：`plugins/file_duplicate_finder/` + 引擎 `plugins/common/DuplicateFinder.{h,cpp}`
    （四级流水线各自可单独调用：`scan` / `groupBySize` / `filterBySampleHash` / `confirmByFullHash`，
    外加纯函数 `suggestDeletions`）。**引擎不删任何东西** —— 删除由插件经
    `Win32::moveToRecycleBin()`（`IFileOperation` + `FOF_ALLOWUNDO|FOF_NO_UI`）执行，
    满足"先扫描后删除、只进回收站"。扫描在后台线程 + 取消令牌，抽样大小由面板的"抽样 KB"控制
    （这个值会写回配置，不是摆设）。每组**保留字典序最小的那份**并在表格里标出"保留/建议删除"。
    实现偏差（有意）：用的是"后台线程 + 排队进度回界面"，没上 `QtConcurrent` ——
    递归枚举本身是 IO 密集、要串行喂四级流水线，线程池在这里只增加复杂度。
    自检断言：四级流水线逐级对得上（4 候选 → 1 组 → 抽样筛掉 1 个 → 确认 1 组 3 个）、
    **抽样读的字节数远小于全量**（状态栏如实报出）、表格"保留/建议删除"逐行正确、
    真正点一次「移到回收站」后**回收站条目数 +2**（`SHQueryRecycleBinW` 差分 ——
    这是"没被硬删"唯一的硬证据）、保留项与无关文件一个都没动。
    ⚠ 副作用：这两次搬运会留在用户回收站里（无法程序化还原），用例输出里已明说。
    留给手测：10 万文件规模下的可中断性（本用例只用 5 个文件跑通链路的正确性）

- [x] **P2-04 剪贴板历史管理** — `input.clipboard_history` · M · 无提权
  - 合并功能：**剪贴板历史 + 剪贴板隐私清理**（D4 决策，二者共享唯一监听器）

  - **自检断言**（`power_group.cpp` 的 P2-06 段，27 条）：锁定是唯一不需要提权的动作（纯函数断言，

- [x] **P2-07 定时任务** — `monitor.scheduler` · S · 部分 ▲提权
  - 实现：`QTimer` + `QDateTime` 调度，触发上述电源能力/静音/提醒
  - 功能：定时关机、定时静音、定时提醒；关机前 60 秒托盘倒计时
  - 可选：调用 `schtasks.exe` 注册到任务计划程序（用户要求时可开关）
  - 验收：跨零点与系统休眠恢复后调度不丢任务
  - **产出**：共享件 `plugins/common/ScheduleEngine.{h,cpp}`（**纯函数**：`nextDailyFire` /
    `dueTasks` / `advanceSchedule` / `nextFireTime` / 任务的 JSON 序列化）+ 插件
    `plugins/monitor_scheduler/`（任务表 + 添加/删除/启停 + 倒计时 + 托盘徽标）。
  - **核心语义（决定了"休眠恢复不丢任务"）**：任务存的是**绝对触发时刻** `nextFireAt`，
    "每天 09:00"只是排定它的规则；调度器每秒只判断 `now >= nextFireAt`。
    于是系统睡了三个小时醒来，错过的那条任务照样被捞出来执行，并**如实标注「补触发」**。
    反过来的边界也定死了：`nextDailyFire()` **严格晚于 now** ——
    用户 09:01 设"每天 09:00"不该立刻弹一个提醒出来（那叫惊吓不叫提醒）。
    推进下一次触发以**排定时刻**为基准而不是以 now 为基准（否则"越睡越偏"）。
  - **第二条纪律**：**电源类任务不立刻执行**，到点后进同一个 `PowerCountdown`（默认 60 秒，可配），
    用户半夜被定时关机打断时至少还有一次反悔机会；任务在**开始倒计时时就算已处理**（推进/停用），
    取消倒计时不等于撤销任务。
  - **有意裁剪**：**不注册到任务计划程序（`schtasks.exe`）** —— 真注册进去之后，卸载插件/停用功能
    都会留下一条系统级计划任务，与本项目"停用即完整还原"的契约（架构约定 9）冲突；
    要"开机即生效"的场景把 WinEase 放进启动项更符合这个产品的模型。
  - **自检断言**（`power_group.cpp` 的 P2-07 段，36 条）：
    纯函数段 —— 跨零点（23:30 排"每天 07:00"→ 次日）、当天未到排在当天、**时刻正好等于 now 时
    严格排到下一次**、跨月（9/30 23:00 排"每天 01:00"→ 10/1）、**休眠三小时唤醒后错过的任务被捞出
    并标记 `missed`**（未来/已停用的不掺和）、每天任务推进到下一次、一次性任务触发后停用；
    端到端段 —— 预置任务的 `nextFireAt` 落在**过去**（这就是"休眠后唤醒"的同一种状态），
    于是启用瞬间就该：提醒任务**弹通知**（且文案里有「补触发」）、静音任务**真的改系统麦克风**
    （读回确认）、电源任务进入**可取消倒计时**而不是立刻黑屏 → 取消后**没有请求发出** →
    另一条电源任务倒计时走完 → 请求带着 `action=shutdown` 真的发出去 →
    配置里的任务一条都没丢（每天任务排到下一次、一次性任务停用）→ 面板添加/删除任务

    收尾把麦克风状态写回用户原值并读回确认。

- [x] **P2-08 亮度 / 色温 / 护眼模式** — `display.brightness` · L · 无提权
  - 合并功能：**亮度色温 + 护眼模式**（D4 决策，同一条 gamma 管线，拆开会互相覆盖）

  - **产出**：平台层 `src/win32/DisplayControl` 补上**内置屏亮度通路**（WMI `root\WMI`：

  - **三条设计纪律**（都被自检钉住）：
    ① **亮度不自己记状态**：面板上的数字永远是**刚从系统读回来的真值**（5 秒轮询一次）——
      用户按 Fn 键、拖系统托盘、按显示器自己的按钮改亮度，面板必须跟着变；也正因如此**亮度不持久化**；
    ② **色温是叠在系统上的滤镜**：启用时捕获每块屏的原始 ramp 当基准，之后每次调节都基于**同一份基准**
      重算（否则多次调节层层叠加会把画面搞花），停用时**逐元素还原**；
    ③ **停用还原色温、但不还原亮度**（有意例外，与 `media.mic_mute` 的 fail-closed 同类）：
      屏幕现在多亮就是用户眼前的样子，把它改回去才是**新的副作用**。
  - ⚠ **实测结论（重要，别再假设）**：Windows 对 gamma 幅度有**硬上限**。本机（内置屏 `SDC420B`）
    实测**能写到 3500K，3250K 被系统拒绝**，而且 `SetDeviceGammaRamp` 是**静默拒绝** ——
    返回 FALSE 但 `GetLastError()` 是 0，照原样报出去就成了"设置 gamma ramp 失败：成功"（已改文案）。
    阈值与 "每通道 ramp 最大值不得低于约 **32768（0x8000）**" 吻合：3250K 蓝通道末级 32459 < 32768 被拒、
    3500K 的 36208 通过。**因此自检先探测本机可写范围、再用实测档位做断言**（换机器不会假失败），
    并额外断言"系统拒绝的档位必须**如实报错**、且不留下半套滤镜"。
  - 界面措辞：6500K 在面板上是「6500K（不调色）」并直接还原原始 ramp ——
    `colorTemperatureGains(6500)` 并不等于一组全 1.0（实测 R 1.000 / G 0.997 / B 0.981），
    套上去会引入谁也说不清的偏色。状态行逐屏列出"走的哪条路"，
    例如「`WMI 内置屏（笔记本面板，eDP 直连不进 DDC/CI 总线）`」。
  - 自检断言（`display_group.*` 的 P2-08 段，**28 条**）：面板色温显示的值来自**配置**（预设 5000，
    不是默认 6500）→ 读回 ramp **逐元素**等于「原始 ramp × 该色温增益」（5000K / 4000K 两档都验）→
    改档后结果仍基于**同一份原始基准**（不是在上一次结果上再乘一次）→ 6500K 逐元素回到原始 →
    夜间时段**覆盖**当前时刻即自动切夜间色温（时段判断**不靠等时间**：改设置立刻生效，跨午夜也验了）→
    时段不含当前时刻则回到日间 → 系统拒绝的档位如实报错 + 不留半套滤镜 →
    面板设亮度则**系统亮度真的变了**（读回确认）→ **绕开插件改亮度、面板 5 秒内跟上**（不自己记一份状态）→
    停用则 gamma 逐元素回到启用前、而亮度**保持现状** → 收尾把亮度写回用户原值。

  - **产出**：共享件 `plugins/common/DeviceUsageMonitor.{h,cpp}`（纯函数：注册表键名 ⇄ exe 路径、
    FILETIME ⇄ Unix 毫秒、"正在使用"判定、条目排序、警报筛选；外加一个**只读**的
    `readConsentStore()`）+ 插件 `plugins/security_device_alert/`
    （轮询 1~60 秒可配、托盘徽标、气泡提示、已批准名单、面板明细）。
  - **四条纪律**：
    ① **"正在使用"只有一个判据**：`LastUsedTimeStart != 0 && LastUsedTimeStop == 0` ——
       从没用过的空键（两个值都是 0）**不算**使用中。算错了用户一启用就被一堆假警报淹没；
    ② **"读不到" ≠ "没人用"**：父键不存在是**正常**的（这台机器还没有任何应用碰过这个设备），
       但读取出错必须如实报出来 —— 对安全类功能来说，"没有警报"和"看不见"完全不同
       （与 P2-10 麦克风静音同一条纪律）；
    ③ **同一个应用只提醒一次**：3 秒一轮的轮询里，通知按 (设备, 键名) 去重，只在**新出现**时弹 ——
       每轮都弹的话用户第一件事就是把这个功能关掉；
    ④ **本插件对注册表只读**：`ConsentStore` 一个字节都不写（唯一写的是用户自己点的"已批准"名单，
       存在 WinEase 自己的配置里）。
  - **"记住已批准"的语义**：名单存**注册表键名**；批准后不再触发提醒，但**仍显示在明细里**
    （看得到、不打扰）。移出名单时会**同时清掉"已提醒过"标记** —— 否则用户会看到
    "徽标亮了却再也不弹通知"，以为移出没用。
  - **自检断言**（`device_group.cpp`，48 条）：
    纯函数段 —— 路径 ⇄ 键名往返（`\` ⇄ `#`）、展示名取可执行文件名、包标识型条目原样显示、
    **空键不算使用中**（★ 最容易犯的错）、FILETIME ⇄ Unix 毫秒往返（0 → -1 而不是 1970 年）、
    空键不进列表、正在使用排最前、警报 = 使用中 ∧ 未批准、徽标文字按设备组合（摄/麦/摄麦/空）；
    端到端段 —— 在 `ConsentStore\webcam\NonPackaged` 下**造一条自检专用记录**
    （键名 = 编码后的 `C:\WinEaseSmoke\camera_smoke.exe`，只写两个时间戳、**不写 Value**）→
    启用插件 → **5 秒内**亮起徽标（"摄"）+ 弹气泡 + 状态/明细点出是哪个应用 +
    「批准」按钮直接写出它会批准谁 → **同一个应用只弹一次**（等两轮轮询通知数不变，但徽标保持亮着）
    → 点「批准」→ 名单落到配置、徽标熄灭、状态回到"没有应用在使用"、明细里仍看得见 →
    点「移出名单」→ 名单清空、提醒重新亮起**并且重新弹通知** →
    把夹具记录改成"已停止使用" → **提示自动解除**（验收原文）→ 停用插件后连轮询都停了 →
    收尾**删除夹具并断言注册表里不留残留**（连读两遍确认）。
    ⚠ 副作用：`ConsentStore` 里会短暂出现一条假记录（系统「隐私」页面能看到），用例结束即删除。
  - ⚠ 过程中修掉一个真实缺陷（踩坑 #57）：`onEnable()` 里**同步**调 `poll()` 会因为
    `isEnabled()` 还是旧值而**弹不出通知**（徽标亮了、气泡没弹）—— 而那正是"没在看托盘"的用户
    最需要的那次提醒。改成排到事件循环下一轮再检查。

- [x] **P2-14 环境变量管理** — `dev.env_manager` · M · 部分 ▲提权
  - 实现：读写 `HKCU\Environment`（免提权）/ `HKLM\...\Environment`（▲）+ 广播 `WM_SETTINGCHANGE`
  - 功能：PATH 可视化编辑、重复项/无效路径检测、变量展开预览、导入导出
  - 验收：修改后新开的 cmd 立即生效；PATH 重复项被正确识别
  - **产出**：共享件 `plugins/common/EnvTools.{h,cpp}`（PATH 拆分/归一化/去重、变量名校验、
    `%VAR%` 展开、条目体检、导入导出 **全纯函数**；外加只读的 `readEnvironment()`）+
    插件 `plugins/dev_env_manager/`（作用域切换、变量表、PATH 条目列表与上下移、
    去重、展开预览、导入导出）。
  - **两条写通道，能力与风险完全不同**：
    ① **用户变量**（`HKCU\Environment`）—— 免提权，平台层直写注册表 + 广播
       `WM_SETTINGCHANGE("Environment")`；
    ② **系统变量**（`HKLM\...\Session Manager\Environment`）—— 经提权助手 `setEnvVar`
       （助手内部会广播）；**缺助手时禁用「保存」并如实说明**，不假装成功。
  - **三条设计取向**：
    ① **空条目不隐藏**：`;;` 与首尾分号产生的空条目在 PATH 里等价于「当前目录」，
       是真实的安全隐患也是常见手滑，必须原样列出来；
    ② **重复项要能定位**：归一化（去引号 / 去尾部反斜杠 / 大小写不敏感）后比较，
       并指出"与第几条相同"，而不是只说"有重复"；
    ③ **未定义的变量原样保留**（不静默变空串）：用户一眼能看出是哪个变量没定义，
       而不是得到一条"看起来正常实则残废"的路径。
  - ⚠ **一条刻意的克制**：「去重」**只改编辑区、绝不自动落盘**，PATH 的保存必须由用户
    再点一次「保存 PATH」。PATH 是"能让一堆程序突然找不到"的东西，任何自动写入都是在赌用户的手速。
  - **自检断言**（`dev_group.cpp` 的 P2-14 段，46 条）：
    纯函数段 —— 按 `;` 拆分且**空条目一个都不丢**、重复项**定位到第几条**、拆分→拼回**逐字符往返**、
    去重同时去空并保留首次顺序、变量名校验（中文 / 数字开头 / 空格 / 连字符全部拒绝）、
    `%VAR%` 展开（**大小写不敏感**、未定义原样保留）、条目体检（存在 / 不存在 / 含未展开变量）、
    导出→导入完全往返、非法 JSON 被拒并给出原因；
    端到端段 —— 默认作用域是用户变量 → 变量表行数 == 注册表项数 → PATH 列表条数 == 真实 PATH 条目数 →
    真实 PATH 有问题条目时界面标出（若本机恰好没有则如实说明，用纯函数断言覆盖）→
    **点「去重」用户 PATH 一个字节都没变**（只改编辑区）→ 写一个**自检专用变量**：
    回读注册表确认真的写进去了 + **抓到 `WM_SETTINGCHANGE("Environment")` 广播**
    （这就是"新开的 cmd 立即生效"的机制）+ 变量表自动刷新 → 删除后注册表里真的没有了 + 同样广播 →
    系统级变量**经提权助手发出**（`setEnvVar`，scope/name 正确）且 **HKLM 没有被真的写入** →
    没有提权通道时系统级「保存」被禁用且如实说明、切回用户变量立刻恢复可用 →
    收尾确认用户环境变量里没有自检留下的任何东西。
    ⚠ 副作用：会真的写一个自检专用用户环境变量（`WINEASE_SMOKE_ENVVAR`，用完立刻删除并回读确认）。
    ⚠ **未覆盖项**：PATH 的「保存」动作**没有在自检里执行**（那会真写用户的 PATH）；
    写通道由"变量保存/删除"那两条覆盖。真落盘 + 助手侧 `setEnvVar` 需要 helper 在运行
    （`elevation_smoke --with-uac` 才是全量路径）。
    ⚠ 验收里的"新开的 cmd 立即生效"：自检进程启动的子进程**必然**继承自检进程的环境块，
    所以从自检里起 cmd 是验不到的 —— 这里验的是**机制**（注册表真的变了 + 广播真的发了），
    那两条加起来正是"任何监听该广播的程序都会刷新环境"的完整证据链。
