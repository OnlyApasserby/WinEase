>
> 1. **P3-01**：最初拿 **shell 窗口**当探针目标，`GetWindowDesktopId` 返回
>    `TYPE_E_ELEMENTNOTFOUND` —— 差点把"用错了目标窗口"误判成"API 在本版本失效"。
>    改成**三个目标（自建已显示窗口 / 控制台窗口 / shell 窗口）各试一遍**后结论反转成"完全可用"。
> 2. **P3-10**：初版只试了 **1 个 CLSID × 2 个 IID**，两个 IID 都返回 `E_NOINTERFACE`，
>    于是写下"未公开接口已失效 → **必须降级**"。补上另一个已知 CLSID
>    （`CPolicyConfigVistaClient`）后，**`CPolicyConfigVistaClient` + `IPolicyConfigVista`
>    返回 `S_OK`** —— 接口一直都在，只是**新类的那个组合不成立**：
>    | 组合 | 结果 |
>    |---|---|
>    | `CPolicyConfigClient` + `IPolicyConfig` | `E_NOINTERFACE` |
>    | `CPolicyConfigClient` + `IPolicyConfigVista` | `E_NOINTERFACE` |
>    | `CPolicyConfigVistaClient` + `IPolicyConfig` | `E_NOINTERFACE` |
>    | **`CPolicyConfigVistaClient` + `IPolicyConfigVista`** | **`S_OK`（拿到了）** |
>
> **共同教训**：探测未公开接口时，**"类 × 接口"的已知组合要全部试一遍** ——
> 只试一种组合就说"不支持"，和"用错目标窗口"是同一类错误。
> **预研的第一责任是别把结论搞反**（这次是反方向：把好消息误判成了坏消息，
> 而这个错误足够严重 —— 它会让我们白白砍掉一个能做的功能）。

  - ★★ **本项最重要的结论：核心功能受系统限制，是"实测出来的降级"（不是没做）**
    —— ROADMAP 原文的「**把当前窗口移到指定虚拟桌面 / 窗口跨桌面搬迁**」
    **用公开 API 做不到**，证据是自检里的**零副作用权限探针**
    （把窗口搬到"它当前所在的桌面"：成功与失败都不改变任何东西，却正好回答"系统让不让我碰这个窗口"）：

    | 样本 | 结果 |
    |---|---|
    | **WinEase 自己**的应用窗口 | **允许**（`S_OK`） |
    | 探针**子进程**的窗口（跨进程、同一份 exe） | **拒绝**（`E_ACCESSDENIED`） |
    | **第三方程序**的窗口（用户正开着的那个） | **拒绝**（`E_ACCESSDENIED`） |

    → **`MoveWindowToDesktop` 只允许搬本进程自己的窗口**。这条限制**官方文档一个字都没写**
    （页面只写"成功返回 S_OK"），社区经验说的是对的，本工程用三档探针把它钉成了可复现的事实。
    ⇒ 于是"**把别人的窗口挪到另一个桌面**"用公开 API 是做不到的；而唯一的替代路（替用户按系统自带的
    `Win+Ctrl+Shift+←/→`）要求目标恰好是**当前活动窗口**、要**抢用户焦点**、依赖用户没改过键位、
    没有相邻桌面时还什么都不发生。**2026-09-14 按用户要求定案：搬移与实验性通道一并砍掉**，
    本项只保留"告诉你那个窗口跑到哪个桌面去了"（只读，不动任何东西）。✂ 见裁剪记录 **C10**。
  - ✂ **曾经落地、随后被砍掉的实验性通道（留档，免得以后又"灵光一现"重新提它）**：
    2026-09-14 当天确实按用户要求实现过一个「模拟按键搬移」实验性选项 —— 替用户按 Windows 自带的
    `Win+Ctrl+Shift+←/→`，纪律也配齐了（**默认关闭** / 发键前**连续稳定确认前台就是目标窗口**、
    非活动窗口直接拒绝 / 发键后**读回确认**并如实汇报）。它技术上能跑，但**用户随后决定整条砍掉**：
    这个功能要抢焦点、依赖系统键位、还会真的改变窗口所在桌面，而换来的只是"少按一次系统快捷键" ——
    一个**只该被阅读**的功能不值得让用户承担这些代价。于是平台层的
    `requestMoveActiveWindowToAdjacentDesktop()` / `moveWindowToDesktop()` / `requestDesktopSwitch()`
    与插件里的开关、按钮、快捷键**一并删除**（自检直接断言"面板上没有搬移 / 切桌面 / 实验性控件的残留"，
    见下）。
  - 自检断言（`p3_group.cpp` P3-01 段按只读一览**重写**，源码里 28 处断言）：只用公开接口就能探测桌面
    （枚举窗口反查 GUID，免提权）、**★★ 恰好有"一个"桌面被标为当前**（实测踩过：被 DWM 隐去的窗口

  - ★★ **最重要的一条设计结论（是自检把它逼出来的）**：
    **Restart Manager 的 `RmCritical`(=1000) 不能当"系统关键进程"判据。**
    它的官方含义是一句**结论**——"这单装不下去了，得重启才能释放"，而成因有三种：
    ① 它确实是关键进程；② **当前进程没权限关它**；③ **它就是发起查询的这个程序自己**
    （Restart Manager 不可能建议"把你自己关掉"）。
    **本机实测**：同一份 `feature_smoke.exe`，作为**查询方**被标 `type=1000`，
    作为**普通子进程**被标 `type=5`（控制台程序）。初版拿它当"禁止结束"，

- [x] **P3-14 USB 设备管控** — `security.usb_control` · M · 部分 ▲提权
  - 实现：SetupAPI 枚举可移动卷 + `CM_Request_Device_Eject` / `IOCTL_STORAGE_EJECT_MEDIA`
  - 功能：一键弹出全部 U 盘、设备插拔记录
  - ✂ **「禁用新 USB 设备」已裁剪**：需改注册表 + 重启生效，一旦出错可能锁死自己（见裁剪记录）
  - 验收：多个 U 盘可逐个/一键安全弹出，占用中的设备给出明确原因
  - ✅ **预研结论（2026-09-14，`p3_spike` + 平台层 `src/win32/StorageDevices`）**：
    ① ★ **不能用 `GetDriveType() == DRIVE_REMOVABLE` 判"可移动"** ——
       **移动硬盘在 Windows 里几乎总是被报成 `DRIVE_FIXED`**，旧判据会**静默漏掉它**
       （而它恰恰是最需要安全弹出的那类设备）。正确判据是
       **PnP RemovalPolicy**（`SPDRP_REMOVAL_POLICY`）+ **总线类型**（`BusType == BusTypeUsb`），
       两者有一条成立就算可移除。已在用户插着的移动硬盘上实测通过：
       `I: Generic · NTFS · 238.5 GB · USB · 可随时拔出`；
    ② ★ **弹出机制分两条**：`IOCTL_STORAGE_EJECT_MEDIA` 只对 U 盘/光驱有效
       （对移动硬盘返回"不支持"）→ **移动硬盘必须走 `CM_Request_Device_Eject`**
       （等价于系统的「安全删除硬件」）；
    ③ ★ **"占用中给出明确原因"有比预想更好的答案**：`CM_Request_Device_Eject` 的
       **veto 机制会带回阻止者的名字**（`PNP_VetoWindowsApp` → 应用名、
       `PNP_VetoWindowsService` → 服务名、`PNP_VetoOutstandingOpen` → 还有未关闭的句柄），
       比自己扫全系统句柄便宜得多也稳得多 → 本项**可以承诺"说清是谁在占用"**；
    ④ **自检绝不真弹出**（用户硬盘上有数据）：自检覆盖"枚举 + 属性 + 判据正确 + 错误中文化"，
       真正的弹出动作**留手测**；
    ⑤ 产品形态建议：**逐个弹出 + 二次确认 + 明确显示是哪块盘**（卷标 + 容量 + 盘符），
       **不做"一键全弹"**（移动硬盘上很可能正在备份）。
