## 架构前置说明（为什么 P0 必须先行）

46 项原始需求中共有 **7 项**依赖全局低级钩子（`WH_KEYBOARD_LL` / `WH_MOUSE_LL`）：
鼠标手势、滚轮增强、按键映射、文本快速扩展、焦点高亮、快速预览（空格键）、剪贴板隐私过滤。

低层钩子对**安装它的线程**有硬约束（必须有消息泵、回调必须极快，超时会被系统静默摘除）。
若每个插件各自 `SetWindowsHookEx`，会产生重复回调、互相抢事件、一个插件卡顿导致全局鼠标变慢。

**结论**：钩子宿主必须是主程序里的唯一单例（`HookService`），插件通过 `PluginServices` 订阅事件。
同理，悬浮窗（5 项功能要用）与提权通道（6 项功能要用）也必须先统一。

## UI 主题：强制黑底白字（2026-09-13 用户插单，不计入 50 项）

> 用户要求：「把全局样式表改成**强制性的黑底白字**，并且**固定不变**，
> 不随操作系统的浅色/深色模式偏好自动切换。」
> 这是在波次推进中途插入的一项，优先级高于继续写模块 —— 因为它决定所有功能卡片
> 与设置对话框的基础观感，越晚改返工面越大。

**改法（三件事必须同时做，缺一件都会"部分跟随系统"）**

1. **样式表**：`src/resources/style.qss` 全量深色（14478 字节，303 条声明，70 条 `background`）
2. **调色板**：`ThemeManager::applyForcedDarkTheme()` 显式设定
   `Window/WindowText/Base/Button/Highlight/...`，**包括最易漏的 3D 边框五色**
   （`Light/Midlight/Mid/Dark/Shadow`）—— 漏掉这五个，控件的立体边框会露出系统浅色
3. **控件样式**：`QStyleFactory::create("Fusion")` 覆盖平台默认样式。
   Windows 11 平台样式（`QWindows11Style`）**会跟随系统应用模式自动切换浅色/深色**，
   只改样式表和调色板而不换样式，是这套需求里最容易漏的一道。
   另加 DWM 标题栏深色接管（`DarkTitleBarFilter`）

**验收：新增 `tests/theme_smoke`（第四套自检）**

- 直接把**真实的 `ThemeManager.cpp` 编进测试目标**（不在测试里抄一份实现），
  并用与主程序相同的资源前缀 `/winease` 注册同一份 `style.qss` + 11 个 SVG
  → 检查的就是主程序真正加载的东西
- 四层证据链：静态扫描（样式表里禁用 `palette(...)`/`color-scheme`/`@media`，
  并逐条扫描全部 `background` 是否为深色）→ 样式层（底层样式必须 `QFusionStyle`）
  → 调色板层 → **实际渲染像素层**（真取像素，不只看属性）
- ★ 抗系统切换：向本进程所有顶层窗口投递系统切浅色时真正会发的消息
  （`WM_SETTINGCHANGE "ImmersiveColorSet"` / `WM_THEMECHANGED` / `WM_SYSCOLORCHANGE`），
  之后断言样式 / 色彩方案 / 调色板 / 3D 色 / **实际像素**全部未变
- ★ 系统浅色下从零启动：临时把 `AppsUseLightTheme` 置 1，然后
  **另起子进程**（`--child-light-probe`）从零启动复验，结束后恢复原值并回读校验

**结果**

| 场景 | 命令 | 结果 |
|---|---|---|
| 系统深色下启动 | `theme_smoke.exe` | **37 / 37 通过，exit 0** |
| 系统浅色下启动 + 抗切换消息 | `theme_smoke.exe --with-os-light-mode` | **41 / 41 通过，exit 0** |

浅色场景的关键证据（子进程输出）：
`平台色彩方案 = Light`、`应用主题前的控件样式 = QWindows11Style`
（证明子进程**真的**处在浅色系统里，不是假场景）→ 应用主题后
`底层样式 = QFusionStyle`、`Window = #000000`、`WindowText = #FFFFFF`、
窗口 (4,4) 实际像素为纯黑。

**未自动覆盖**：DWM 标题栏颜色**无法用 API 读回**（只能断言 `DwmSetWindowAttribute`
返回成功），需肉眼确认；自检在结尾打印了该提示。

## 界面信息层级调整：卡片只放两行 · 说明迁到帮助（2026-09-14 用户插单，不计入 50 项）

> **用户要求（原话）**：卡片的功能介绍改成"固定两行和完整文本 Tooltip"，
> "标识和版本号以及完整实现全部迁移到帮助（新增『关于插件』栏目）"。

**问题在哪**：卡片只有 **336×150**，原来把**名称 / 标识 / 版本 / 描述 / 状态 / 开关 / 设置按钮**
全塞进去 —— 描述按固定字数（46 字）硬截断，而标识与版本号挤占的正是"人真正要读的那两行"的空间；
偏偏"这个功能做不到什么"这类内容是最该被读的，却只能显示两行。

**改法（三件事，缺一件都不算完成）**：

| # | 改动 | 关键实现 |
|---|---|---|
| ① | 描述**固定两行** | `FeatureCard` 按描述标签的**实际宽度**用 `QTextLayout` 逐行排版，超出两行就在第二行落点截断并补 `…`；描述区高度恒为 2 × 行距（**短描述也不会让卡片矮一截**） |
| ② | **完整描述进 Tooltip** | 卡片与描述标签的 Tooltip = `plugin->description()` 全文 |
| ③ | **标识 / 版本 / 完整说明迁到帮助** | 主程序的 `QMessageBox::about` 换成**栏目式** `HelpDialog`（左栏「关于 WinEase」「关于插件」）：后者每个插件一段 = 名称 + **标识** + **版本号** + 作者 + 完整说明（`detailedDescription()`），被崩溃隔离的插件**照实标注原因** |

**两条设计约束（写进代码注释，避免以后被"顺手优化"掉）**：

- **帮助页只走"缓存读"**：插件元信息一律用 `PluginManager` 的 `idOf/nameOf/versionOf/...` ——
  崩溃被隔离的插件**不能再调用它的任何方法**，缓存读让"插件已经死了"这件事不阻碍界面**如实展示它为什么死**。
- **长文本只有一个落点**：卡片上**不再出现**标识与版本号（自检直接断言"卡片文字里不含 id / 版本号"）。
  否则"迁移到帮助"就变成"两边各有一份"，以后必然不同步。

**验收（新增第 9 套自检 `tests/ui_smoke`，18 条 / exit 0）**：

- 卡片：真实插件**逐张**检查"最多两行 / Tooltip == 完整描述 / 描述区高度 == 2 × 行距 /
  卡片文字里无标识无版本号"；
- ★ **人造超长描述样本**：一个描述**一定**超过两行的 `IFeaturePlugin` 桩 —— 把"压到两行 + 省略号"
  这条路径**确定性地**逼出来（若真实插件描述碰巧都短，上面那批断言会退化成"短文本原样显示"，等于没测）；
- 帮助：栏目数量与名称、**切栏目真的换了内容页**（不是只列在左边）、**每个插件一段**、
  **每个插件的标识与版本号都能查到**、写了完整说明的插件其说明出现在页面上、
  「关于 WinEase」仍写着版本号与插件目录。

## 每个任务的验收标准（Definition of Done）

1. 编译 **0 error / 0 warning**（本工程 `/W4`）
2. **可完整卸载**：钩子注销、托盘/悬窗销毁、注册表项清理、gamma/透明度/层级等系统状态**恢复原样**
3. 快捷键冲突走 `GlobalHotkeyManager::validateSequence()` 并给出**中文原因**
4. 需要提权的操作走 **`WinEaseHelper.exe`**，失败有明确提示而非静默失败
5. 异常被插件边界捕获，**不拖垮主程序**（WinRT 的 `hresult_error` 必须转为错误码，禁止穿透）
6. 插件停用/重新启用可来回切换且不泄漏资源
7. 提供自测步骤说明（写入对应插件的 `README` 或本文档条目下）
